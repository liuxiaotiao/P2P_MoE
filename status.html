两条互不包含的依赖

控制机

numpy + tokenizers + jinja2。不装 torch —— 一个张量都不碰。装了就会有人让它"顺手算一层"，那条路一开，时序测量立刻失真。

推理节点

numpy + torch + safetensors。不装 tokenizer —— 节点自始至终只见 token id，文本在控制机的入口编码、出口解码。

两条边界各有一条测试守着（test_requirements.py）。本轮加 curl 传输时它当场抓到了一次违规：我在 fetch.py 里 import 了 tokenizers 去校验文件，而那个模块跑在 15 台节点上。

03验证到什么程度

最硬的一条证据：执行层与官方实现逐元素一致。Qwen3-Next 的前向（36 层 Gated DeltaNet + 12 层全注意力、共享专家、零中心 RMSNorm、部分旋转 RoPE）与 transformers 对齐到 prefill 1.7e-05、decode 完全相同、分段切分逐位一致。

另一条：驻留集只要包含实际被路由到的专家，输出与全装逐位一致 —— 「只驻留子集」不是近似，是无损。

还没验的

  • 真权重上的数值。合成 checkpoint 的权重是随机的，验的是机制不是数值。fetch 跑完这一条就能补上。
  • 真实负载下的时延与算力使用率。这正是 measure 要产出的东西。
  • drop-expert 的质量损失。工具已就绪（examples/drop_expert_impact.py），量三件事：miss 率、丢掉的门控质量、输出 KL 与生成分叉步。还没在真权重上跑过。

04真实数据推翻的三个预期

三个 CSV（gsm8k / math / mbpp 的逐专家激活）+ 真实 15 节点拓扑，跑出来的结论和方案假设差得不小。

① math_expert_activation.csv 有采集 bug，不能用。层 3–47 的专家 0–9（正好 = top_k）计数正常但 mean_weight 是 nan。这些专家在受影响层里占 27–30% 的计数，不是边角。按 0 处理会把它们永远排除在驻留集外，而它们可能恰恰是最热的。gsm8k 与 mbpp 干净。

② 激活远没有方案假设的那么集中

文档假设实测（90% 覆盖）
后段每层驻留全集的 10–20% gsm8k 197/512（38%）、mbpp 224/512（44%）

细粒度比 51 说的是「单 token 只碰 2%」，但聚合到整个数据集，热专家的尾巴很长。这一条直接决定了后面所有内存账 —— 3:5 的任务比在这个池子上根本放不下（需要 8 条通道 = 577 GB，池子只有 321 GB）。最终落到 覆盖率 0.70、mbpp 2 条 + gsm8k 1 条。

③ 任务重叠度没有拐点

本来想从「前段任务无关、后段任务相关」的分界找 L₀，但逐层 Jaccard 在 48 层里始终在 0.36–0.65 之间震荡，没有趋势（层 0 是 0.603，层 47 是 0.553，周期约 12）。所以改用可识别性 p(L₀)：Bhattacharyya 距离 → Chernoff 界，拐点在 L₀=11，p ≥ 97.69%。

覆盖率与通道数不是单调的。0.70 → 负载比 0.94×，0.60 → 1.25×，0.50 → 0.83×。段的组成是离散的、跳数是整数，所以挨个试比推理快。

顺带补进来的能力

断点续传

链路中途掐断时按已收字节续。实测每次只传 137 字节也能把 256 KB 拼齐，逐字节一致。

curl 传输通道

Python 的 TLS 下不动时整轮改用 curl。切换是粘的 —— 上万个张量不能每次先失败一遍。

局域网权重源

serve-weights：一台下全量，15 台从它切片。python -m http.server 不支持 Range，用不了。

逐台体检

doctor：代码 / 解释器 / torch / 权重 / 端口 / 磁盘 / 日志，15 台并行几秒出结果，还会替你找出 conda 里带 torch 的那个解释器。

LFS 指针识别

GIT_LFS_SKIP_SMUDGE=1 克隆出来的目录看着完全正常，每个分片却只有 130 字节文本。

源站诊断

diag：小文件与大文件是不是两个域名、CDN 那个通不通。企业白名单漏放 CDN 时用它定位。

06还差什么

优先级条目说明
跑完就有真权重上的数值验证 合成 checkpoint 只验了机制。fetch 完成后即可对照
跑完就有时延与算力使用率 measure 的产出，工具与报表都已就绪
P0画像收敛判据 采多少 token 才够，现在全凭手感。应看逐层分布的 TV 距离随样本量的变化
P0增量补拉与断点续 改了覆盖率之后只补差额，而不是重下整份
P1采样策略 现在后段 tail 是 argmax。要 temperature / top-p / repetition penalty 与可复现的种子口径
P1连续批处理 当前是每条通道排他独占一条请求
P1通道一（SPRT）与三层维护 方案里的在线自适应部分，目前是静态放置 + 盲绑 + 换绑
P2中继横向扩展、池合并、方向不对称修正 都有明确的触发条件，现在还没到

一条要反馈给方案作者的偏差：文档假设后段驻留集是全集的 10–20%，实测是 38–44%。这不是实现问题，是数据的性质 —— 但它让「3:5 任务比」这类基于内存账的设计目标在真实池子上放不下。后续的容量规划都该按实测值重估。
