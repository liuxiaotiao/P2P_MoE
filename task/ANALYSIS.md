# 真实数据上的规划结果（Qwen3-Next-80B，15 节点）

数据：`task/{gsm8k,mbpp,math}_expert_activation.csv` + `task/topo_fabric_mbps.json`
口径：激活度 = `count × mean_weight`（总门控质量），用 **decode 相**。

---

## 0. 先说三件与预期不符的事

### ① `math_expert_activation.csv` 有采集 bug，不能用

层 3–47 的**专家 0–9**（正好 = top_k）计数正常但 `mean_weight` 是 `nan`：

```
3,0,81804,402914,nan,nan     ← 计数 40 万，权重丢了
3,10,85,667,0.064485,0.071396 ← 专家 10 起正常
```

这些专家在受影响层里占 **27–30% 的计数**，不是边角。按 0 处理会把它们永远
排除在驻留集外，而它们可能恰恰是热的。gsm8k 与 mbpp 干净（0 处异常）。

### ② 激活远没有方案假设的那么集中

| | 文档假设 | 实测（90% 覆盖） |
|---|---|---|
| 后段每层驻留 | 全集的 10–20% | **gsm8k 197/512 (38%)、mbpp 224/512 (44%)** |

细粒度比 51 说的是「单 token 只碰 2%」，但**聚合到整个数据集，热专家的尾巴很长**。
这一条直接决定了下面所有内存账。

### ③ 「前段重合、后段分化」这个前提，数据不支持

两个 task 的 90% 驻留集 Jaccard 在 48 层里震荡于 0.36–0.65，**没有趋势**：
层 0 是 0.603，层 47 是 0.553。共用比各装省下的比例每个 L₀ 都是 ~33%，与深度无关。
震荡周期约 12 层，与层型（线性/标准注意力）只有弱相关（0.476 vs 0.518）。

所以**不能用重合度曲线找拐点** —— 它没有拐点。

---

## 1. 前段拐点：用 p(L₀)，不是用重合度

文档 III.5.3 用 p(L₀)（前 L₀ 层能否认出 task）选切点，但没说曲线从哪来。
这里从激活数据直接推：逐层算两 task 门控质量分布的 Bhattacharyya 距离，
累加后用 Chernoff 界转成判别准确率下界。

| L₀ | p(L₀)≥ | 边际增益 | 前段并集(本层) | 累积 |
|---:|---:|---:|---:|---:|
| 4 | 78.77% | +10.41% | 256 | 1363 |
| 6 | 89.62% | +3.74% | 295 | 1930 |
| 8 | 92.14% | +1.04% | 357 | 2650 |
| **11** | **97.69%** | +1.33% | 229 | **3385 ← 膝点** |
| 13 | 99.08% | +0.71% | 212 | 3855 |
| 21 | 99.90% | — | — | 6100 |

**膝点 L₀ = 11**（最大弦距法），此时 p ≥ 97.7%，前段 22.1GB。

**这条曲线是乐观上界。** 它假设各层的判别证据独立，而真实路由沿层相关
（前面选了什么会影响后面），所以累加会高估可分性。保守起见 L₀ 该往大取 —— 
99% 需要 L₀=13。

## 2. 3:5 的任务比：**这个池子支撑不了**

3:5 要精确表达至少需要 8 条通道。而：

| 覆盖率 | 前段/条 | 后段/条 | 单通道 | 8 条需要 | 缺口 | 池子够几条 |
|---:|---:|---:|---:|---:|---:|---:|
| 0.95 | 24.9GB | 61.4GB | 86.3GB | 690GB | 369GB | 3.7 |
| **0.90** | **22.1GB** | **50.0GB** | **72.2GB** | **577GB** | **256GB** | **4.4** |
| 0.80 | 18.1GB | 36.0GB | 54.1GB | 433GB | 112GB | 5.9 |
| 0.70 | 14.6GB | 26.7GB | 41.3GB | 330GB | 9GB | 7.8 |
| 0.60 | 11.4GB | 19.8GB | 31.2GB | 250GB | 0 | 10.3 |

池子可用总量 **321GB**（12×24GB + 3×16GB，各扣 1GB 预留、再乘 0.95 可用率）。

**在 90% 覆盖下只够 4.4 条**（精确位配平 3 条，θ=0.8 折扣后 N_work=2）。
2 条通道无法表达 3:5，最大余额法给出 1:1。

### 实际跑出来的两个配置

**A. 覆盖率 0.90（你要求的）→ 2 条通道，配额 1:1**

```
L₀=11；前段 2 条、后段 gsm8k 1 条 + mbpp 1 条
ch0  gsm8k  F1(N09)          → Bgsm8k0(N07,N08,N06)  组合 p50 24.4ms
ch1  mbpp   F0(N01,N02,N10)  → Bmbpp0(N05,N03,N04)   组合 p50 23.2ms
终审：最坏相对极差 3.5% vs η=15% → 通过
```

**B. 覆盖率 0.70 → 3 条通道，配额 mbpp:gsm8k = 2:1**

比 1:1 更接近 3:5（目标 0.625:0.375，实得 0.667:0.333）。代价是每层只留
26.7GB 的后段，drop-expert 的损失要用 `examples/drop_expert_impact.py` 量过再定。

### 要真正做到 3:5，三条路

1. **降覆盖率到 0.60**（10.3 条）—— 质量代价未知，先量 KL；
2. **加机器**：90% 覆盖下 8 条需要 577GB，即再加约 11 台 24GB；
3. **改比例**：4 条通道能表达 1:3；8 条才有 3:5。若「3:5」只是流量比而非通道比，
   可以用 2 条通道 + 按 3:5 分发请求（排队时长自然拉开），不必物理隔离。

## 3. 拓扑的两个观察

**没有抖动维度。** JSON 只给了确定的 `propagation_delay`，没有 p95 或抖动。
于是文档里的尾闸（β）与抖动闸（J_cap）**恒定通过** —— 公共中值域比真实分散
环境宽松得多，规划出的通道数偏乐观。`--jitter-frac` 可注入抖动做敏感性分析。

**接入质量差异大。** 单向 p50 从 0.03ms 到 13.5ms。规划器自动把最好的入口
（N05/N03/N01，各 1ms）留给了段的端点，最差的三台（N13/N14/N15，各 12ms）
被排除在出口集之外 —— 三台 T4 同时也是仅有的 16GB 机器，两个劣势叠加。

## 4. 怎么跑

```bash
python examples/task_deploy.py --data ./task --tasks gsm8k=3,mbpp=5 \
    --coverage 0.90 --save-plan plan.json --save-spec deploy.json

# 敏感性：覆盖率 / 切点 / 注入抖动
python examples/task_deploy.py --data ./task --coverage 0.70 --l0 11
python examples/task_deploy.py --data ./task --jitter-frac 0.3
```
