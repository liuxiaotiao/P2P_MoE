# 5:3 随机到达能不能直接测

**能，但要走动态路径。** 静态配对（`--static`）下一条前段绑死一个 task，
随机来的请求它接不住。文档主线正是为这个设计的。

## offline 提前组织的是什么

**不是**「给每条请求排一条固定路」，**是**「保证任意前段配任意同 task 后段都不后悔」
—— 公共中值域（II.3）+ 组合矩阵。所以池子建好之后，到达序列怎么排都不用再安排。

实测（覆盖率 0.70，400 条请求，mbpp:gsm8k = 5:3）：

```
L₀=18（p≥99.85%），前段 3 条，后段 gsm8k 2 条 + mbpp 1 条，组合矩阵 9 组

前段使用: F0=134  F1=133  F2=133          ← 盲绑，均匀
出现过的组合:
  F0 配过 [Bgsm8k0, Bgsm8k1, Bmbpp0]
  F1 配过 [Bgsm8k0, Bgsm8k1, Bmbpp0]
  F2 配过 [Bgsm8k0, Bgsm8k1, Bmbpp0]
→ 9/9 组全部被用到
```

识别准确率 100%（理论下界 99.85%）。**但这是乐观上界** —— 逐请求直方图是从
聚合分布 i.i.d. 采样的，真实请求的 token 高度相关、方差更大、更容易跨界。
要真数得按请求粒度采激活。

## 真正的问题：5:3 的到达比，建出来的产能是 1:2

| task | 到达占比 | 产能占比 | 负载/产能 | 每条后段接了 |
|---|---:|---:|---:|---:|
| gsm8k | 36.2% | 66.7% | **0.54×** | 72 条 |
| mbpp | 63.7% | 33.3% | **1.91×** | 255 条 |

**不是配额算错，是建不出来。** 规划日志：

```
[Step 2] 配额 {'gsm8k': 2, 'mbpp': 2}；公平比 gsm8k=1.33、mbpp=0.80（瓶颈池 mbpp）
[Step 3] task mbpp 第 2 条被质量下限否决：用了 7 跳，而剩余池的跳数下界只有 1
[Step 3] 实建少于配额（mbpp 少 1 条）→ 修正后配额 {'gsm8k': 2, 'mbpp': 1}
```

根因：**mbpp 的驻留集更大**（0.70 覆盖下层均 117/512 vs gsm8k 的 94），
后段一条 24.2GB vs 19.8GB。gsm8k 先建完之后，剩下的机器凑不出一条不超跳数
下界的 mbpp 段。并发度 = 通道数，所以超出的部分不是变慢，是**排队**。

## 怎么办：逐 task 用不同覆盖率

覆盖率不必全局统一 —— 谁重就压谁：

| mbpp 覆盖 | gsm8k 覆盖 | 建出来 | mbpp 负载/产能 |
|---:|---:|---|---:|
| 0.70 | 0.70 | gsm8k 2 + mbpp 1 | 1.88× |
| **0.60** | **0.70** | **mbpp 2 + gsm8k 2** | **1.25×** ← 最优 |
| 0.50 | 0.70 | gsm8k 2 + mbpp 1 | 1.88× |
| 0.40 | 0.70 | gsm8k 2 + mbpp 1 | 1.88× |

**0.60 是甜点，再降反而变差** —— 因为段的构成是离散的，
更小的驻留集不一定换来更好的分段（跳数下界是整数）。

降 mbpp 覆盖率的质量代价要用 `examples/drop_expert_impact.py` 在真权重上量过再定。

## 怎么跑

```bash
python examples/task_arrival_sim.py --data ./task --mix mbpp=5,gsm8k=3 \
    --coverage 0.70 --requests 400

# 真机上：不加 --static 就是动态路径
python3 -m p2pmoe.deploy.control --agents ... --model-dir /data/qwen3-next-part \
    --tasks mbpp=5,gsm8k=3 --profile prof.json --coverage 0.70
```
